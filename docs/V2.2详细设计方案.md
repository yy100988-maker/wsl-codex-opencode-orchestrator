## 1. 编写目的

本文件基于以下输入整理 WSL 版 V2.2 的详细设计：

1. WSL 仓库现有脚本：`admission-cycle.sh`、`supervisor-loop.sh`、`common.sh`、`process-manager.sh`、`worktree-manager.sh`、`preflight.sh`、`lease-manager.sh`、`state-rebuild.sh`。
2. Windows 原生仓库文档：[Windows 版 V2.2 优化方案与详细设计](../codex-opencode-orchestrator/docs/2.2优化方案与详细设计.md) / `[[../codex-opencode-orchestrator/docs/2.2优化方案与详细设计.md]]`。
3. WSL 版 V2.1 已交付或草案能力，包括任务拆解、双向内存准入、cgroup 限制、孤儿扫描、Gate、temporary worktree 清理等。

本文件只描述设计，不包含代码改动。代码实施应在文档评审通过后按实施计划推进，并单独获得同意。

## 2. V2.2 范围

WSL 版 V2.2 严格对齐 Windows 版 V2.2 的五个未完成方向，同时保留 WSL 专有差异。

1. 内存压力自适应配置化阈值、配置化降级比例、Level 3/4 高内存任务清理。
2. `orphan_scan_interval` 周期控制的孤儿进程扫描，并修复现有事件 JSON 写入问题。
3. 进程健康监控：CPU、内存、日志推进、进程消失、健康快照落盘、告警和收敛动作。
4. 事件日志压缩与归档，并保持 `state-rebuild.sh` 可恢复摘要事件。
5. worktree 空间回收与磁盘清理，路径边界保持 fail-closed。

非本期范围：

- 不引入新语言运行时，保持 Bash + jq + Linux proc/ps 工具。
- 不替换 Windows 原生 PowerShell 编排器。
- 不改变任务拆解、Gate、Grok provider、WSL cgroup 等 V2.1 已有主题的整体边界。

## 3. 现状核对

### 3.1 已具备

| 能力 | 现有实现 | 说明 |
|---|---|---|
| WSL/Windows 双侧内存采样 | `admission-cycle.sh` + `host-memory-guard.ps1` | 已读取 WSL `free` 与 Windows `host_used_percent` |
| 基础自适应并发 | `admission-cycle.sh#adaptive_concurrency()` | 硬编码 70/80/85/90 阈值，未配置化 |
| 孤儿扫描调用点 | `supervisor-loop.sh#scan_orphans()` | 已按 `cycle_count % orphan_scan_interval` 触发 |
| 进程超时/无进展判定 | `supervisor-loop.sh` | 已有 `max_task_runtime_seconds` 与 `stall_timeout_seconds` |
| cgroup WSL 内存限制 | `preflight.sh#ensure_cgroup_limit()` | 已支持 `memory.wsl_max_mb` |
| Flow 状态目录 | `common.sh#wsl_ensure_state_dirs()` | 已创建 `events/`、`metrics/`、`archives/`、`worktrees/` |
| Gate 通过后 worktree 删除 | `supervisor-loop.sh` + `worktree-manager.sh remove` | 正常路径已清理 |

### 3.2 缺口

| 缺口 | 影响 |
|---|---|
| 内存阈值、降级比例不可配置 | 无法按机器水位平滑降级，无法按配置完成 Level 3/4 回收 |
| 自适应并发只取 WSL 单侧 | 与 V2.1 设计“取 `max(wsl, host)` 作为压力依据”不一致 |
| Level 3/4 高内存清理未实现 | 内存接近临界时没有按峰值内存回收任务 |
| `orphan-killed` 事件写入疑似无效 JSON | 当前 `"{"pid":$child_pid}"` 不会按预期展开 |
| 无 `metrics/health.jsonl` | 无法审计 CPU 高占用、内存快速增长、stall、进程消失 |
| 无事件压缩 | 长时间运行后事件目录膨胀 |
| 无 `worktree-manager disk-recovery` | 磁盘超过阈值后不能自动清理过期 archive 和残留 worktree |
| `state-rebuild.sh` 不支持 summary 事件 | 事件压缩后可能破坏恢复能力 |

## 5. 内存压力自适应配置化

### 5.1 现状与目标

现状在 `admission-cycle.sh` 中写死：

```bash
adaptive_concurrency() {
  local used=$1 max=$2
  if (( used < 70 )); then echo "$max"
  elif (( used < 80 )); then echo $(( max * 70 / 100 ))
  elif (( used < 85 )); then echo $(( max * 40 / 100 ))
  elif (( used < 90 )); then echo $(( max * 10 / 100 ))
  else echo 0
  fi
}
```

V2.2 改为从配置读取 `pressure_levels` 和 `concurrency_reduction`，并让调度输入使用双侧内存最大值：

```bash
max_used=$(( wsl_used > host_used ? wsl_used : host_used ))
effective_max=$(adaptive_concurrency "$max_used" "$max_concurrent" "$pressure_levels_json" "$reduction_json")
```

### 5.2 压力等级判定

```bash
get_memory_pressure_level() {
  local used="$1"
  local max_concurrent="$2"
  local pressure_levels_json="$3"
  local reduction_json="$4"
  local cleanup_json="$5"

  # 输出 JSON：
  # { "level": 0|1|2|3|4,
  #   "used_percent": <used>,
  #   "adaptive_concurrent": <number>,
  #   "kill_count": <number>,
  #   "action": "none"|"reduce"|"reduce-and-cleanup"|"stop-and-cleanup" }
}
```

判定规则：

| 条件 | Level | 动作 |
|---|---:|---|
| `< level1_percent` | 0 | 全额并发 |
| `< level2_percent` | 1 | 并发乘 `reduction.level1`，至少 1 |
| `< level3_percent` | 2 | 并发乘 `reduction.level2`，至少 1 |
| `< level4_percent` | 3 | 并发乘 `reduction.level3`，至少 1，并触发高内存清理 |
| `>= level4_percent` | 4 | 并发为 0，停止准入，触发高内存清理 |

### 5.3 Level 3/4 清理

在 `admission-cycle.sh` 中新增 `invoke_memory_pressure_cleanup`：

```bash
invoke_memory_pressure_cleanup() {
  local config="$1"
  local state="$2"
  local root="$3"
  local level="$4"
  local kill_count="$5"
  local dry_run="$6"

  # 1. 读取 active entries。
  # 2. 对每个 task pid_file，读取 /proc/<pid>/status 的 VmRSS 作为 peak_rss_mb。
  # 3. 只保留 worktree 路径位于 "$root/.opencode/worktrees/" 内的任务。
  # 4. 按 peak_rss_mb 从高到低排序。
  # 5. 取前 kill_count 个任务。
  # 6. dry_run：只写 memory_pressure_cleanup_started 候选列表。
  # 7. 非 dry_run：process-manager.sh stop、worktree-manager.sh archive、
  #    释放 Lease、将任务标记 blocked，
  #    并写 memory_cleanup_kill 事件。
}
```

安全边界：

- 只允许清理 `active` 中 `status=running` 或 `status=admitted` 的任务。
- 只允许清理 PID/PGID 与 `processes/<task_id>.json` 匹配且 worktree 路径受控的任务。
- 禁止按进程名全局 kill，例如 `pkill node`、`pkill bun`。
- 清理完成后写 `memory_pressure_cleanup_completed`。

### 5.4 状态记录

新增事件：

```text
memory_pressure_cleanup_started
memory_cleanup_kill
memory_pressure_cleanup_completed
admission-paused
```

记录内容至少包含 `level`、`used_percent`、`effective_max`、`kill_count`、`task_id`、`peak_rss_mb`。

## 6. 孤儿进程周期扫描

### 6.1 现状问题

`supervisor-loop.sh` 已有周期调用点，但存在以下问题：

```bash
wsl_append_event "$state" orphan-killed "$id" "{"pid":$child_pid}"
```

这段代码不会按预期产生合法 JSON。V2.2 需要改为：

```bash
wsl_append_event "$state" orphan-killed "$id" "$(jq -cn --argjson pid "$child_pid" '{pid:$pid}')"
```

### 6.2 扫描逻辑

将 `scan_orphans` 升级为 `invoke_orphan_process_scan`：

```bash
invoke_orphan_process_scan() {
  local state="$1"
  local root="$2"
  local config="$3"

  # 1. 遍历 $root/.opencode/processes/*.json。
  # 2. 仅处理 status == running 的记录。
  # 3. 校验 pid、pgid、start_time、cwd。
  # 4. 若根 PID 已不存在，扫描 PGID 或 cwd 关联存活子进程。
  # 5. 仅向受控任务 PID/PGID 发 SIGTERM，宽限期后 SIGKILL。
  # 6. 写 orphan-killed / orphan-recovered 事件。
  # 7. 更新 orchestrator-state.last_orphan_scan_at。
  # 8. 写 orphan_scan_completed 汇总事件。
}
```

触发条件继续使用：

```bash
cycle_count=$((cycle_count + 1))
if (( cycle_count % orphan_scan_interval == 0 )); then
  invoke_orphan_process_scan "$state" "$root" "$config"
fi
```

验收标准：

- 默认 `orphan_scan_interval=5` 时，5 轮内发现根进程已死但子进程存活的记录。
- 清理只针对当前任务 PGID 和受控 worktree，不误杀其他项目。
- 每次扫描都更新 `last_orphan_scan_at` 和事件日志。

## 7. 进程健康监控

### 7.1 健康采集

`process-manager.sh` 新增 `health` 子命令：

```bash
bash scripts/process-manager.sh health <state> <task-id>
```

输出示例：

```json
{
  "task_id": "A1-auth-contract",
  "pid": 1234,
  "process_name": "opencode",
  "status": "alive",
  "status_detail": null,
  "memory_mb": 320.5,
  "cpu_seconds": 45.2,
  "log_path": ".opencode/logs/A1-auth-contract.log",
  "log_age_minutes": 2.0,
  "cwd": ".opencode/worktrees/A1-auth-contract",
  "sampled_at": "2026-08-22T08:00:00Z"
}
```

采集来源：

- 存活状态：`kill -0 <pid>`。
- 内存峰值/当前 RSS：`/proc/<pid>/status` 的 `VmRSS`。
- CPU：`/proc/<pid>/stat` 的 `utime + stime`，或 `ps -o cputime=`。
- 日志推进：读任务 `log` 字段对应文件的 `stat -c %Y`。
- 进程名：`/proc/<pid>/comm`。
- 任务上下文：`processes/<task_id>.json` 的 `pid/pgid/start_time/cwd/log`。

### 7.2 健康判定

在 `supervisor-loop.sh` 新增 `get_process_health_state`：

| 条件 | 判定 | 原因 |
|---|---|---|
| 进程不存在 | `dead` | `process-exit` |
| `log_age_minutes > health_stall_timeout_seconds / 60` | `stall` | `no-output` |
| 窗口内内存增长超过 `health_growth_mb` | `warning` | `memory-growth` |
| 两次 CPU 采样换算使用率大于 `cpu_high_percent` 且持续 `cpu_high_duration_seconds` | `warning` | `cpu-high` |
| 以上都不满足 | `alive` | `normal` |

采样历史只保留必要窗口：

```bash
declare -A HEALTH_SAMPLES
# 每个 task_id 保存：
# { previous: { sampled_at, cpu_seconds, memory_mb }, current: { ... } }
```

### 7.3 落盘和动作

每轮 Supervisor 将健康快照追加到：

```text
<root>/.opencode/metrics/health.jsonl
```

动作：

- `dead`：立即进入终态清理流程，写 `process_dead` 事件，停止进程记录、释放 Lease、更新任务为 `blocked`。
- `stall`：写 `process_stall` 事件；若超过 `stall_timeout_seconds` 仍未恢复，沿用现有超时保护。
- `warning`：写 `health_warning` 事件；连续 `health_warning_persist_threshold` 轮写 `health_warning_persistent`，不立即终止进程。

`report-builder.sh` 应支持读取 `metrics/health.jsonl`，在资源清理报告中增加健康采样表。

## 8. 事件日志压缩

### 8.1 新增脚本

建议新增 `scripts/event-store.sh`，提供：

```bash
wsl_compress_events() {
  local events_dir="$1"
  local archive_dir="$2"
  local full_keep_days="$3"
  local summary_start_days="$4"
  local archive_after_days="$5"
}
```

### 8.2 压缩规则

事件文件格式为 `events/<YYYY-MM-DD>.jsonl`。

```text
最近 full_keep_days 天：保留完整 JSONL。
full_keep_days 到 archive_after_days：抽取摘要到 <YYYY-MM-DD>.summary.jsonl，删除原始行。
超过 archive_after_days：整段归档到 .opencode/archives/events/<YYYY-MM-DD>.jsonl 或 .summary.jsonl。
```

摘要字段：

```text
event_type
timestamp
task_id
data.status
data.reason
```

保留事件类型：

```text
task-*
gate_*
memory_*
orphan_*
health_*
disk_recovery_*
events_compressed
```

### 8.3 安全要求

- 使用事件目录锁和临时文件，避免压缩中途损坏。
- 摘要文件必须能被 `state-rebuild.sh` 读取。
- 归档文件不作为实时状态来源。
- 压缩完成后写 `events_compressed` 事件。

### 8.4 `state-rebuild.sh` 适配

`state-rebuild.sh` 当前只读取：

```bash
find "$events" -type f -name '*.jsonl' ...
```

V2.2 应同时读取 `*.jsonl` 和 `*.summary.jsonl`，不读取 `archives/`。否则事件压缩后，状态重建会丢失最终状态。

## 9. worktree 空间回收

### 9.1 新增能力

`worktree-manager.sh` 新增 `disk-recovery` 子命令：

```bash
bash scripts/worktree-manager.sh disk-recovery <root> <config>
```

或独立函数：

```bash
invoke_disk_recovery() {
  local root="$1"
  local config="$2"
  local dry_run="$3"
}
```

### 9.2 回收流程

每次 `cycle_count % disk_recovery_interval == 0` 时检查 `.opencode/` 目录大小。

```text
size_mb > threshold_mb 后依次执行：

1. 删除超过 archive_max_age_days 的过期任务归档（archives/*，排除 archives/events）。
2. 删除已完成且已通过 Gate 的残留受控 worktree。
3. 删除超过 failed_archive_max_age_days 的失败任务归档。
4. 每次删除前校验路径仍位于 ControlledRoot 或明确归档目录内。
```

路径校验必须使用：

```bash
wsl_is_within "$candidate" "$root/.opencode/worktrees"
wsl_is_within "$candidate" "$root/.opencode/archives"
```

### 9.3 事件

```text
disk_recovery_check
disk_recovery_delete
disk_recovery_completed
```

每条删除记录包含 `path`、`reason`、`size_mb`、`dry_run`。

## 10. 集成与调用链

```text
supervisor-loop.sh
  ├─ 启动：preflight + cgroup + 事件压缩首次执行
  ├─ every cycle:
  │   ├─ 事件压缩（cycle_count % event_compress_interval == 0）
  │   ├─ 孤儿扫描（cycle_count % orphan_scan_interval == 0）
  │   ├─ 健康快照 -> metrics/health.jsonl
  │   ├─ 磁盘回收（cycle_count % disk_recovery_interval == 0）
  │   └─ admission-cycle.sh
  │        ├─ 读取双侧内存 max(wsl, host)
  │        ├─ adaptive_concurrency 配置化降级
  │        ├─ Level 3/4 invoke_memory_pressure_cleanup
  │        └─ 启动候选任务
  └─ 长运行后：事件压缩与归档
```

建议等待状态锁释放后调用磁盘回收，避免与任务创建/合并同一批状态文件发生竞争。

## 14. 风险与兼容

- 所有新配置必须带默认值；缺失配置时回退到 V2.1 行为。
- WSL 版继续使用 `max(wsl_used, host_used)` 作为压力依据，避免只监控单侧导致 Windows 主机内存过高。
- Level 3/4 清理只处理受控 worktree，避免误杀其他项目。
- 健康采样必须限制历史窗口，避免内存无界增长。
- 事件压缩、磁盘回收均 fail-closed；不能删除无法确认路径边界的文件。
- WSL 版与 Windows 版保持独立实现，不以 PowerShell 脚本替代 Bash 脚本。
