## 3. 任务拆解策略

### 3.1 问题诊断

从 crm-app 项目实际运行观察：

- 任务 T4->T6 串行执行，T6 等 T4 完成才启动
- 根因：depends_on 设置过宽，非必要依赖导致任务链拉长
- 结果：22GB 内存只用了 63%，CPU 只有 7%，硬件严重空闲

### 3.2 文件级拆分规则

**规则 1：每个源码文件 = 一个独立任务**

- service 文件：每个 service 独立任务
- controller 文件：每个 controller 独立任务
- 页面组件：每个页面独立任务
- 测试文件：跟随对应源码文件

**规则 2：共享文件串行化**

- types/interfaces：单文件串行任务，所有依赖它的任务挂 depends_on
- config/routes：单文件串行任务
- 数据库迁移：单文件串行任务
- 入口文件（index/main）：最后执行

**规则 3：依赖关系最小化**

- 只在必须共享类型/接口时才设置 depends_on
- 不同模块的文件之间零依赖
- 同一模块内的文件按调用链排序，但尽量解耦

**规则 4：任务粒度控制**

- 单任务预计修改 1-3 个文件
- 单任务预计代码量 50-300 行
- 单任务内存估算 512MB（opencode + Node.js 运行时）
- 单任务超时上限 3600 秒

### 3.3 拆分示例（crm-app）

当前 crm-app src/ 结构：

```text
src/
  services/
     timeline-service.js
     customer-service.js
     order-service.js
     email-service.js
  routes/
     timeline-routes.js
     customer-routes.js
  middleware/
     auth.js
  db/
     migrations/
  index.js
```

拆分方案：

```text
Phase 1（无依赖，全并行）：
  T1: timeline-service.js + timeline-service.test.js
  T2: customer-service.js + customer-service.test.js
  T3: order-service.js + order-service.test.js
  T4: email-service.js + email-service.test.js

Phase 2（依赖 Phase 1 的类型，串行）：
  T5: timeline-routes.js（depends_on: T1）
  T6: customer-routes.js（depends_on: T2）

Phase 3（最后执行）：
  T7: auth.js（无依赖，可与 Phase 1 并行）
  T8: index.js（depends_on: T5, T6）
```

### 3.4 依赖消除技巧

**技巧 1：提前锁定共享类型**

主控 agent 在拆分前先创建 types.ts / interfaces.ts，所有子 agent 只引用不修改，消除类型文件的竞争。

**技巧 2：Mock 依赖接口**

子 agent 实现 service 时，用 mock 替代对其他 service 的直接调用，Gate 验收时再做集成测试。

**技巧 3：接口契约先行**

主控 agent 先定义所有 API 接口契约（request/response schema），子 agent 按契约实现，不需要等其他 agent 完成。

**技巧 4：数据库 Schema 先行**

主控 agent 先完成所有 migration，子 agent 只操作已有的表，不修改 schema。

## 4. 并行执行优化

### 4.1 调度器参数调优

| 参数 | V2.0 默认 | V2.1 建议 | 理由 |
|---|---|---|---|
| max_concurrent_agents | 5 | 15 | 22GB 内存可支撑 15 个 agent |
| max_new_agents_per_cycle | 1 | 5 | 每轮多启动几个，加快铺开 |
| monitor_interval_seconds | 30 | 15 | 调度更灵敏，资源利用更紧凑 |
| max_task_runtime_seconds | 7200 | 3600 | 文件级任务 1 小时足够 |
| stall_timeout_seconds | 600 | 300 | 更快发现卡死任务 |
| task_start_delay_ms | 500 | 200 | 缩短任务启动间隔 |

### 4.2 内存估算模型

单个 OpenCode agent 内存构成：

```text
opencode 进程本身：约 200MB
Node.js 运行时：约 150MB
项目 node_modules（共享，不重复计算）：约 100MB
工作内存（prompt + 上下文）：约 60MB
合计：约 512MB / agent
```

22GB 内存分配：

```text
Windows 系统 + 桌面应用：约 6GB
WSL VM 预留：约 2GB
可用于 agent：约 14GB
理论最大并发：14GB / 512MB = 27 个
安全上限（80%）：约 15 个
```

### 4.3 启动优化

**优化 1：批量启动**——每轮调度周期启动 max_new_agents_per_cycle 个任务，而不是逐个启动。

**优化 2：并行 worktree 创建**——worktree-manager.sh create 支持后台执行，多个 worktree 同时创建。

**优化 3：共享依赖预装**——第一个 agent 触发 pnpm install，后续 agent 复用 node_modules（通过 worktree 共享）。

**优化 4：模型预热**——主模型首次调用有冷启动延迟，第一个 agent 启动后，后续 agent 复用连接。

## 5. 并行测试与验收

### 5.1 三层测试策略

**层级 1：任务级单元测试**（每个 agent 自带）

- agent 完成代码后立即运行自己的测试
- 测试失败则 agent 自行修复并重试
- 不阻塞其他任务

**层级 2：Gate 验收**（任务完成后立即执行）

- 不等所有任务完成
- 通过则立即合并到主分支
- 失败则标记 blocked，归档 worktree

**层级 3：集成测试**（所有任务完成后）

- 全量回归测试
- 跨模块交互验证
- 性能基准测试

### 5.2 Gate 并行化

```text
当前流程（串行）：
  agent 完成 -> 等待 -> Gate 验收 -> 合并 -> 下一个

优化后流程（并行）：
  agent 完成 -> 立即 Gate 验收（不阻塞其他 agent）
                通过 -> 立即合并
                失败 -> blocked + 通知主控
```

实现：gate-runner.sh 已支持独立调用，supervisor-loop.sh 每轮扫描所有 gate_pending 任务，并行执行多个 Gate。

### 5.3 合并策略

**策略 1：乐观合并**——Gate 通过后立即 git merge，冲突时由主控 agent 解决。

**策略 2：批量合并**——每 5 个任务完成后批量合并一次，减少 merge 冲突概率。

**策略 3：分支保护**——每个任务分支只允许修改 allowed_files，Gate 检查文件范围，防止越界。

## 6. 硬件性能压榨

### 6.1 内存利用

目标：从 63% 提升到 80%+。

当前状态：

| 指标 | 值 |
|---|---|
| 总内存 | 22GB |
| 已用 | 14GB（63%） |
| 空闲 | 8GB |
| VmmemWSL | 1.9GB |

优化措施：

1. `windows_reserve_mb` 从 4096 降到 3072，释放 1GB 给 agent
2. `wsl_stop_admission_percent` 从 88% 降到 82%，允许更多任务运行到更高水位
3. `max_concurrent_agents` 从 5 提到 15，调度器允许更多并发
4. 目标：14GB + 3.8GB = 17.8GB（80%）

### 6.2 CPU 利用

当前状态：CPU 7%，严重空闲。

优化措施：

1. 增加并行 agent 数量，每个 agent 占用一个 CPU 核心
2. Gate 验收并行执行，不串行等待
3. worktree 创建并行执行
4. 依赖安装并行执行（不同任务的 pnpm install）
5. 目标：CPU 利用率 40-60%

### 6.3 磁盘 IO 优化

当前瓶颈：所有 worktree 在 WSL Linux 文件系统，/mnt/d 跨文件系统 IO 慢。

优化措施：

1. 项目必须在 `/home/<user>/projects/` 下，避免 `/mnt/d` 的跨文件系统开销
2. node_modules 使用 pnpm 硬链接，减少磁盘占用和 IO
3. 日志异步写入，不阻塞 agent 执行
4. worktree 使用 overlay 策略，Git worktree 本身是硬链接，IO 开销小

## 7. V2.1-draft 未实现功能补全

### 7.1 孤儿进程扫描

supervisor-loop.sh 新增 scan_orphans 函数：

- 遍历 `.opencode/processes/*.json`
- 检查每个 running 状态的进程 PID 是否存活
- 若根进程已死，扫描其进程组中的子进程并 SIGTERM
- 每 5 轮 Supervisor 循环执行一次
- 可配置 `orphan_scan_interval`

### 7.2 进程健康监控

process-manager.sh 新增 health 子命令：

- 读取 `/proc/<pid>/status` 获取 VmRSS
- 检查日志文件最后修改时间
- 输出 JSON：`{status, memory_kb, log_age_minutes}`
- 超过 stall_timeout 无日志更新则标记卡死

### 7.3 WSL cgroup 内存限制

preflight.sh 新增 ensure_cgroup_limit：

- 读取配置 `memory.wsl_max_mb`（默认 8192）
- 写入 `/sys/fs/cgroup/memory.max`
- 防止 WSL 消耗过多 Windows 内存

配置：

```json
{
  "memory": {
    "wsl_max_mb": 8192,
    "wsl_swap_mb": 2048,
    "cgroup_enabled": true
  }
}
```

### 7.4 双侧内存协调

admission-cycle.sh 改进：

- 当前：只检查 `wsl_used`
- 改进：取 `max(wsl_used, host_used)` 作为压力依据
- 任一侧达到阈值即降级并发

### 7.5 事件日志压缩

common.sh 新增 wsl_compress_events：

- 保留最近 7 天的完整日志
- 7-30 天的日志只保留 task 相关事件
- 30 天以上的日志归档到 archives/events/
- Supervisor 启动时执行一次，之后每 100 轮执行一次

### 7.6 worktree 空间回收

worktree-manager.sh 新增 disk-recovery 子命令：

- 检查 `.opencode/` 目录大小
- 超过阈值（默认 1024MB）时触发清理
- 删除 30 天以上的归档
- 删除已通过 Gate 的 worktree

1. 任务拆分后，并行度从串行 T4->T6 提升到 10+ 任务同时运行
2. 内存利用率从 63% 提升到 80%+
3. CPU 利用率从 7% 提升到 40%+
4. 单文件级任务完成时间从 2 分钟降到 1 分钟以内

8. 30 天以上的事件日志被自动压缩
9. .opencode/ 目录超过 1GB 时自动清理
